# Job Marketplace API

A small backend API for managing job postings and job applications.

The project was built as a take-home case study to demonstrate:

- REST API design
- Separation of concerns
- Business logic
- Data modelling
- Input validation
- Unit/API testing
- In-memory persistence

## Technology

- Python
- FastAPI
- Pydantic
- Pytest
- Uvicorn

## How to Run

### 1. Clone the repository

git clone https://github.com/iqmalnaaim/job-marketplace-backend-api.git

cd job-marketplace-backend-api

### 2. Install dependencies

pip install -r requirements.txt

### 3. Start the server

uvicorn app.main:app --reload

The API will be available at:

http://127.0.0.1:8000

Interactive API documentation:

http://127.0.0.1:8000/docs

### 4. Run tests

pytest

## API Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| POST | /jobs | Create a job |
| GET | /jobs | List jobs |
| GET | /jobs/{job_id} | Get a job |
| POST | /jobs/{job_id}/close | Close a job |
| POST | /jobs/{job_id}/applications | Apply for a job |
| GET | /jobs/{job_id}/applications | List applications |

## Design Overview

The application follows a layered architecture:

Client
  ↓
Router
  ↓
Service
  ↓
Repository
  ↓
In-memory storage

### Router

Responsible for handling HTTP requests and responses.

The router intentionally contains minimal business logic.

### Service

Contains business rules such as:

- New jobs start as OPEN.
- Closed jobs cannot receive applications.
- A job must exist before an application can be submitted.
- A job cannot be closed twice.

### Repository

Responsible for storing and retrieving data.

The repository currently uses in-memory dictionaries because a database is not required for this exercise.

This abstraction would allow the storage implementation to be replaced with a relational database later without significantly changing the service layer.

### Models

Models represent the application's core entities:

- Job
- Application
- JobStatus

### Schemas

Schemas define the data accepted by API endpoints.

For example, clients do not provide:

- Job ID
- Created timestamp
- Job status

These are generated and controlled by the backend.

## Assumptions

1. Authentication and authorisation are out of scope.
2. A candidate can submit multiple applications because the requirements do not specify a restriction.
3. Location is represented as free text.
4. Job IDs and application IDs are generated by the application.
5. Data is stored in memory and will be lost when the application restarts.
6. Only OPEN and CLOSED job statuses are supported.
7. No pagination is implemented because the expected dataset is small.
8. No frontend is included.

## What I'd Improve With More Time

### Database

Replace in-memory storage with PostgreSQL.

Possible tables:

- jobs
- applications

Applications would have a foreign key referencing jobs.

### Database constraints

Add constraints such as:

- Foreign key from applications.job_id to jobs.id
- NOT NULL constraints
- Appropriate indexes

### Validation

Add stronger validation for:

- Required fields
- String lengths
- Candidate email
- Duplicate applications

### Dependency Injection

Improve repository dependency management so each test can use an isolated repository.

### Pagination

The GET endpoints could support:

- limit
- offset

or cursor-based pagination for larger datasets.

### Error handling

Introduce consistent application-level error responses.

### Logging

Add structured logging for important operations and errors.

### Authentication and Authorisation

If the marketplace became a real application, authentication and role-based authorisation would be required.

For example:

- Employers can create and close jobs.
- Candidates can submit applications.
- Employers can view applications for their jobs.

### Deployment

The application could be containerised with Docker and deployed behind a production web server/load balancer.

## Trade-offs

The implementation intentionally uses in-memory storage rather than a database.

This keeps the solution small and focused on API structure and business logic, which matches the scope of the exercise.

For a production system, a persistent database would be necessary.
